## 1. 为什么要改

联调安阳样例 `docs/samples/01-anyang-zhengwu-yunwei.pdf` 时发现：

1. **`auto` 误推 MinerU**：94 页「原生复杂 PDF」被推荐远程 MinerU；未配置 `MINERU_API_TOKEN` 时任务失败。  
2. **章节过碎**：pdfplumber 输出 `## 第 N 页`，再加宽松标题检测，约 **716** 个 section，大量空壳／页标题。  
3. **B07 尚未起步**：方案要求「六类要求 + 可定位证据」，需要可跑的草稿链路，而不是先换 PostgreSQL。

## 3. 详细说明

### 3.1 解析策略（A）

**文件**

- `backend/bid_agent/parsing/strategy.py`  
- `backend/bid_agent/parsing/document_parser.py`（`_normalize_parse_method` 改为委托 `resolve_parse_method`）  
- `tests/test_parse_strategy.py`  
- `README.md`（自动解析说明）

**行为变化**

| 画像 | 旧推荐 | 新推荐 |
|---|---|---|
| `simple_text_pdf` / `native_text_pdf` | 页数 ≥30 常走 MinerU 并行 | **`pdfplumber`** |
| `mixed_pdf` 且样本页文本够用 | MinerU | **`pdfplumber`**（警告：图片字可能漏） |
| `scanned_pdf` / 无可用文本层 | MinerU | **仍为 MinerU** |

**兼容性**

- 用户手动选择的 `parse_method` 不变。  
- 空／`auto` 统一走 strategy，避免 `document_parser` 与 strategy 两套逻辑漂移。

### 3.2 章节切分降噪（B）

**文件**

- `backend/bid_agent/parsing/document_parser.py`  
- `tests/test_section_split.py`

**要点**

1. pdfplumber 只写 `<!-- page:N -->`，**不再**写 `## 第 N 页`。  
2. `_detect_heading` / `_looks_like_heading`：忽略页标题；带取值的编号行（如 `1.1项目编号：xxx`）、长括号条款、像句子的编号行不当标题。  
3. 新增 `consolidate_bid_sections`：合并历史「第 N 页」碎片，并向后传播 `page_start`／`page_end`。  
4. 删除重复的旧版 `_parse_pdf_with_pdfplumber` 定义（原文件中后者覆盖前者）。

**安阳样例对照（本地 pdfplumber）**

| 指标 | 改前约 | 改后约 |
|---|---|---|
| section 数 | 716 | 295 |
| 「第 N 页」标题 | 94 | 0 |
| 带 `page_start` | 很少 | 全部 |
| 六大章标题 | 有 | 有 |

**注意**：库里**旧解析任务结果不会自动重算**。要看新切分，需对同一版本重新提交解析任务。

### 3.3 B07 结构化要求草稿（C）

**文件**

- `backend/bid_agent/schemas/requirements.py`  
- `backend/bid_agent/services/requirement_extract.py`  
- `backend/bid_agent/repositories/requirements.py`  
- `backend/bid_agent/api/routes/requirements.py`  
- `backend/bid_agent/main.py`（挂载路由）  
- `backend/bid_agent/repositories/platform.py`（migration **v2**：`requirement_items`）  
- `backend/bid_agent/analysis/rule_extractor.py`（项目编号正则支持中文编号）  
- `docs/implementation/b07-draft.md`  
- `tests/test_requirement_extract.py`

**数据模型（摘要）**

每条要求含：`category`（六类）、`field_key`、`title`、`raw_text`、`normalized_value`、`confidence`、`review_status`、`source_refs`（`block_id`／`section_index`／`section_path`／`page`／`quote`）、`extractor_version`（当前 `b07-rule-v1`）。

**API**

```http
POST /api/v1/document-versions/{version_id}/requirements/extract
GET  /api/v1/document-versions/{version_id}/requirements?category=overview
POST /api/v1/requirements/{item_id}/review
```

- `extract` 可传 `job_id`；缺省用该版本最近一次 **succeeded** 解析。  
- 重抽只删除同 `extractor_version` 且 `review_status='draft'` 的行，**保留**已 `confirmed` 等人工结果。

**安阳样例一次实测（基于已有成功解析）**

约 **224** 条草稿：overview 12／qualification 30／rejection 26／commercial 24／technical 109／scoring 23。  
概览可抽到项目名、编号、预算、采购人、代理机构等；多数带 block／页码。技术类噪声偏大——草稿预期内，需后续 LLM／人工筛选。

**已知限制**

- 仅规则／关键词，无 LLM。  
- 无前端确认台。  
- 证据靠文本包含匹配，不是 bbox 级。  
- 章节仍可能偏碎 → 同类条款偏多。

## 4. 如何验证

```bash
# 策略单测（容器内可改用 python -c 断言；完整 pytest 需 dev 依赖）
# 见 tests/test_parse_strategy.py / test_section_split.py / test_requirement_extract.py

docker compose up -d --build --wait
# 工作台对样例 PDF 选「自动」或「本地 PDF」重新解析
# 然后：
curl -sS -X POST "http://127.0.0.1:8080/api/v1/document-versions/<version_id>/requirements/extract" \
  -H 'Content-Type: application/json' -d '{}'
curl -sS "http://127.0.0.1:8080/api/v1/document-versions/<version_id>/requirements?category=overview"
```

改策略／切分／抽取代码后需 **重建 api（及 worker，若解析在 worker）** 镜像，宿主改 Python 不会自动进只读镜像。
